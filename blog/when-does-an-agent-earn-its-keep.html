When Does an Agent Earn Its Keep?

Research question: when does decomposition improve measurable reliability enough to justify its cost?

A multi-agent diagram is not evidence that a multi-agent system is the right system.

Research in progress: matched evidence before architecture claims. The experiment described below is scoped but has not yet been run.

The current conversation about agentic AI often starts with architecture: a planner, a researcher, a critic, a router, and a final writer. The more useful starting point is the decision the system must support. What can the added structure verify? What uncertainty does it preserve? What failure can it stop before it becomes an external action?

This is not an argument against agents. It is an argument for treating decomposition as a hypothesis. If splitting a workflow into stages or agents does not improve the end-to-end result enough to justify its latency, cost, failure surface, and maintenance burden, the simpler system is the better engineering decision.

The science has been studying these choices for a long time

The names have changed, but the design questions are familiar. Earlier speech systems explored modular knowledge sources that exchanged hypotheses through shared working memory. Other systems integrated more of the search and carried multiple plausible alternatives forward. The historical lesson is not that one architecture always wins. It is that committing too early can discard the alternatives a later stage would have needed.

The Hearsay-II retrospective describes the blackboard architecture and its cooperating knowledge sources. The NASA report on Harpy documents a different approach based on integrated search and competing hypotheses. These systems do not settle today’s agent question, but they give us a vocabulary for discussing modularity, shared state, search, and delayed commitment.

What current research is measuring

Current agent research has moved the question from “did the model produce a plausible answer?” to “did the system complete the task in the environment it was given?” That includes tool choice, policy following, state changes, repeated reliability, and whether the benchmark’s task and scoring design justify its claim.

Evaluation research also treats the measurement system as an object of study. A benchmark can vary because of task framing, the environment, the scaffold around the model, the judge, or the reviewer. A score is not automatically a property of the model alone.

That is why my working evaluation practice separates task outcome from evidence quality. A result can look complete while missing the identifier, authorization record, source freshness, or reconciliation evidence needed to support the claim.

What the recent results do not prove

Recent work has found cases where a single model performs as well as or better than a multi-agent system when both receive the same reasoning token budget. Other work studies how multi-agent behavior might be distilled into a single end-to-end model. These are useful results, but they are not a universal rule that one agent is always better.

The correct conclusion is narrower: an architecture comparison is only interpretable when the resources and task are matched. Otherwise, a multi-agent system may appear better because it received more calls, more tokens, more opportunities to retry, or a more favorable task decomposition.

The handoff is part of the measurement boundary

A handoff is the point where one stage gives information to another. Passing only a fluent conclusion can erase the uncertainty that should have changed the next decision. A safer handoff carries the evidence needed to check the conclusion, the alternatives that remain plausible, the source or tool state, and the reason to stop or escalate.

This is the connection to the evaluation work I have been building. An evidence contract defines the minimum observable information required before a result can be treated as usable evidence. The contract does not make an agent correct. It prevents a well-formed response from being mistaken for a supported result.

When does an agent earn its keep?

I would keep the additional architecture only when a matched evaluation shows a benefit that matters to the decision. The comparison should include:

  • end-to-end task outcome, not only intermediate answer quality;
  • evidence completeness and correctness at each handoff;
  • tool and permission correctness;
  • recovery, refusal, stopping, and escalation behavior;
  • latency, token or request cost, and retry amplification;
  • variance across repeated runs; and
  • maintenance cost after a model, prompt, tool, or policy change.

A subagent that performs well in isolation does not prove that the overall workflow is better. The added component has to improve the decision at the system boundary.

The experiment I want to run next

The practical next step is a matched comparison in the Agent Assurance Harness: compare a flat workflow with a multi-agent workflow using the same synthetic cases, tools, budget, permissions, and stopping rules.

A flat workflow means one primary agent loop. A multi-agent workflow adds one or more specialized agents or handoff stages. Both paths would have to produce the same observable evidence before the harness could treat the result as supported.

The experiment would measure whether the extra handoffs improve end-to-end evidence or only add more places for uncertainty to disappear. It would report tradeoffs rather than force a winner. The result might show that a multi-agent path earns its cost for one task family and not another. That would be a useful result.

The comparison is planned, not completed. The existing agent evaluation and release guide already defines the matched-case questions. The next research phase will turn those questions into a frozen protocol before running either architecture.

The decision rule

Start with the simplest workflow that can meet the decision’s evidence requirements. Add an agent, a handoff, or a specialist only when the added structure creates a measurable control, verification boundary, context boundary, or recovery path.

Then test the whole system again after the model, tools, prompts, policies, or environment change. Architecture is not a permanent property of the product. It is part of the measurement claim.

The question I want an agent design to answer is simple: what does this extra component let us know, stop, verify, or recover that the simpler workflow could not?
