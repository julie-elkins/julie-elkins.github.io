Designing AI Evaluations That Can Support a Decision

A measurement system should make clear what happened, what was missing, and what decision the result is allowed to support.

I started building evaluation systems because a green result can still be the wrong evidence for the decision in front of a team.

A model can return a valid-looking answer. A tool call can return HTTP 200. A dashboard can turn both into a green row. None of those facts establishes that the workflow completed the task safely, used the right evidence, or produced a result that is still valid after the system changes.

I am learning to design evaluations from the decision backward. The evaluation is not only a score-producing script. It is the measurement system that tells a team whether the score is strong enough to use.

1. Start with the decision, not the metric

“Did the model answer correctly?” is often too small a question for an agent workflow. A tool-using agent may need to select the correct tool, use an authorized side effect, preserve an operation identifier, detect stale evidence, abstain when required, and report what actually happened.

The decision might be whether to release a workflow, allow it to continue operating, or route a case to a human. Each decision needs a different measurement boundary. If the evaluation measures only answer quality, it can miss the failure that matters most: a successful-looking result that cannot be trusted.

2. Separate task outcome from evidence quality

One of the most useful distinctions in my work is between the outcome and the evidence for the outcome. A task can appear complete while required evidence is absent. Conversely, an agent can safely abstain and provide the evidence needed to show that it did not claim completion.

I use an evidence contract: the minimum observable information required before the harness treats a result as usable evidence. The contract can include a classification, required identifiers, operation state, authorization state, retry count, and bounded cost information.

This is why provider-valid JSON is not the same as valid assurance evidence. A schema can make the output well-formed while the fields still describe an unsupported claim.

3. Test the evaluator, not only the system

An evaluation can fail in two directions. It can miss a real failure, or it can report a failure that the system did not have. Both matter when the result controls release or review work.

That means the evaluator needs its own questions: what is the reference decision, how was it established, how much agreement exists between reviewers, and how much of the result changes when the same measurement is repeated?

In the public response-quality study, the first reviewer round exposed ambiguity in a generic workflow-state field. The result was not a reason to change the provider runs. It was a reason to version the rubric and test whether a revised instrument is easier for independent reviewers to apply.

4. Report refusals and denominators

A refusal is not a successful result, and it should not disappear from the denominator. In the frozen response-quality study, each condition attempted 30 synthetic cases. The public record reports both evidence satisfaction among accepted traces and evidence satisfaction over all attempted cases.

The distinction changes the interpretation. A treatment can make accepted traces look slightly better while producing more refusals, leaving the end-to-end yield of usable evidence lower. Reporting only the accepted traces would hide the operational cost of the refusal surface.

5. Treat system change as a measurement event

Evidence belongs to a particular system revision. A prompt change, tool change, retrieval change, authorization change, evaluator change, or deployment change can make an older reliability claim incomplete even when the stored score remains unchanged.

That is the problem behind my reauthorization study. The question is not whether a prior report was mathematically correct when it was produced. The question is whether it still supports the decision being made after the workflow has changed.

6. Make the limits part of the result

The sentence I want every evaluation to answer is: “What does this result not prove?” A small synthetic matrix can expose a protocol failure without estimating a production failure rate. A live-provider comparison can show a configuration-specific refusal pattern without ranking providers. A reviewer calibration round can expose rubric ambiguity without validating model quality.

Those limits are not an apology attached after the result. They define what decision the result is allowed to support.

The design habit I am keeping: record what was required, what was observed, what was missing, and what the result does not establish.

Where I am going next

I am finishing a second, separately versioned reviewer round for the response-quality study. The provider experiments remain frozen while the human-calibration evidence is collected. That separation matters: changing the rubric is a measurement change, not a way to make an inconvenient provider result look better.

The working artifacts are public in LLM Evaluation Validity. The research paper and its reproducibility materials live there; this article is the explanation layer for readers who want the reasoning before they open the repository.

A practical learning path

If you want to work through these ideas, the Claude Evaluation Lab turns them into a learner path. It begins by separating transport success from task success, then layers deterministic checks, semantic checks, and human review before connecting traces to release and observability controls.

  • Start with the semantic-outcomes lab to see why a successful request is not proof that the task succeeded.
  • Use the Agent Assurance Harness to inspect the executable evidence and control boundary.
  • Use the Agent Systems Design Guide for the shared vocabulary and design patterns.

The required course path is offline and synthetic, meaning it uses bounded local cases rather than live provider requests. The optional live Claude adapter is an extension, not evidence that the course proves live model quality or production readiness.
