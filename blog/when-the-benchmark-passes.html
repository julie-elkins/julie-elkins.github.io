When the Benchmark Passes but the Evidence Fails

A public coding-agent study showed why execution reliability, benchmark correctness, and evidence completeness need separate measurements.

Codex completed all ten matched tasks and passed seven. Mini-swe-agent completed nine and passed six. The more important finding was that a passing task did not automatically prove that the expected evidence existed.

I built a small Harbor Assurance Adapter to run real coding agents through Harbor, the execution framework used for the study, and feed bounded metadata into the Agent Assurance Harness. The harness is a secondary assurance check: it does not judge the agent's reasoning, but it can check whether the run left the metadata required to support a public claim.

The benchmark was Terminal-Bench 2.0, a public coding-agent benchmark. The comparison used the same ten tasks, one attempt per task, the same task-set revision, and the same Finch compatibility path, meaning the same container-execution setup. That boundary made the result more useful, but it did not turn the study into a universal ranking of models or providers.

Three measurements, not one

I separated the study into three questions:

  • Execution reliability: did the agent reach a trustworthy terminal state without a setup, timeout, provider, or transport failure?
  • Benchmark correctness: did the task verifier accept the result?
  • Evidence completeness: did the run leave the bounded metadata and trajectory evidence required by the assurance contract?

These are related, but they are not interchangeable. Counting an agent setup failure as a benchmark failure makes the model look less correct than the observation supports. Counting a benchmark pass as evidence-complete makes the result look more reproducible than it is.

The matched results

Codex, using openai/gpt-5.5, had ten clean executions, ten benchmark observations, and seven passes. That is a 70% pass rate over attempted tasks. The observed Harbor cost was $10.098631.

Mini-swe-agent, using anthropic/claude-opus-4-6, had nine clean executions, nine benchmark observations, and six passes. That is a 60% pass rate over attempted tasks and a 66.7% conditional pass rate among the nine trustworthy observations. The observed Harbor cost was $16.182813.

The tenth mini-swe-agent task failed during agent setup and did not produce a trustworthy benchmark observation. It belongs in the execution-reliability result, not in the conditional benchmark denominator. Reporting both denominators is more informative than hiding the setup failure or treating it as an ordinary task miss.

A reproducibility update

After the initial comparison, I added a local cohort comparator, meaning a no-cost report tool that reads the saved public task summaries without making another provider call. It checks the benchmark and task-set revisions, model and configuration, task count, and attempts before recomputing the metrics from the task records.

The validated follow-up completed all ten mini-swe-agent executions and passed nine tasks. I keep that result separate from the original denominator: it is a new provider execution under recovered environment conditions, not causal proof that one bridge change produced the improvement. The comparison report shows the cohort metrics and task-level deltas.

Claude Code was also exercised, but provider-quota and evidence-path interruptions prevented a fully comparable public ten-task result. I did not infer a leaderboard accuracy score from those partial or diagnostic runs.

A later bounded QEMU compatibility diagnostic, meaning a small troubleshooting experiment for the Linux virtual-machine path, completed cleanly after provider credits were restored. The run produced one clean execution, one benchmark observation, and one benchmark pass; its ATIF v1.2 metadata also passed, with an observed Harbor cost of $0.806020. This remains diagnostic evidence outside the matched denominator. Because the earlier attempt was confounded by provider-credit exhaustion, the result supports the compatibility path under this configuration but does not prove that the explicit instruction alone caused the difference. Read the QEMU diagnostic report.

A small diagnostic changed the interpretation

The raman-fitting task failed after a clean execution because the agent used the native wavelength axis while the verifier expected calibrated Raman-shift units. A unit contract is the explicit statement of which coordinate system and units the output must use.

I ran one bounded ablation, meaning a small experiment that changed one condition: the unit-conversion instruction was delivered directly into the agent's prompt. The run completed cleanly, produced one benchmark observation, passed it, and had an observed cost of $0.198360.

That result supports a task-specific interpretation-sensitivity finding: the explicit unit contract changed the outcome. It does not prove that every under-specified task behaves the same way, so it remains diagnostic evidence rather than a leaderboard result.

The assurance result was separate from the score

In one controlled Claude Code smoke run, a complete local JSONL event log existed while Harbor did not produce an ATIF trajectory file. ATIF, the Agent Trajectory Interchange Format, is the structured trajectory artifact expected by the evidence path. The adapter therefore refused to label the run ATIF-verified and recorded the fallback evidence source explicitly.

That is not a cosmetic distinction. If a task passes but the expected trajectory artifact is missing, a reviewer can know that the answer was accepted without being able to reconstruct the execution evidence in the expected format. A passing score and a complete evidence record are separate properties.

The result I trust most is not the highest score. It is the result whose denominator, failure class, evidence path, and limits are all visible.

What the study does not claim

This is a configuration-specific public study, not a universal model ranking. It does not claim that Codex or mini-swe-agent is always better. It does not add the Raman ablation to the matched denominator. It does not convert provider, setup, timeout, or transport failures into benchmark failures.

The public record also does not publish raw trajectories, prompts, tool arguments, provider responses, credentials, or private content. The observed Harbor cost is a run-level observation, not a guarantee of provider billing. Those boundaries matter because a public evaluation should be reproducible without making sensitive execution content public.

Why I am publishing the awkward parts

A clean leaderboard number is easy to repeat and difficult to interpret when the execution path is hidden. A study that reports refusals, setup errors, missing artifacts, and changed instructions is less tidy, but it gives the reader a better chance of deciding what the result is actually useful for.
